## 独立修复：手机重启后恢复服务

原 Manifest 缺少 BOOT_COMPLETED 接收器。新增 BootRecoveryReceiver，仅在用户此前开启本地服务、已同意协议且无维护/迁移任务时，尝试启动已有前台服务。手动停止后不自动启动。系统拒绝启动时记录待恢复，提示打开工作台；不宣称 QQ 已在线。此修复不能替代原生消息通道问题。

生产 Java 编译和维护回归通过，包括恢复策略、数据迁移、精确补丁、下载续传、签名更新、语音音色策略及网页视频策略。Windows 无符号链接权限，主机符号链接用例明确跳过，不能替代安卓设备验证。

本地包 `七丘QQ工作台-1.0.9-开机恢复.apk`，内部版本 10016，SHA256 为 `b97d56f336f3d5e8081d7fda78ec4379bfd1e7e9faad2cacf3fabcc228c137fc`。构建工具只允许两个固定哈希的已校验底包，逐文件校验保留资源，原 1.0.7 运行库和音色未变。已在 user 0 同签名覆盖安装，系统版本和 BOOT_COMPLETED 接收器注册已核对；67 项配置、记忆、音色文件内容校验保留，其他空间安装状态保留。未进行真实重启验收，不能标记开机恢复或 QQ 端到端修复通过。

## 找到的账号布局不匹配与隔离验证

QQ 确有账号数据库、消息数据库和打开的文件锁；全部 341 个 fdinfo 可读，原生内存读取也成功。继续检查实际 core 候选对象后，发现匹配虚表及虚函数的对象在 `0x230` 保存账号字符串，而 SnowLuma 1.14.22 的读取函数固定读取 `0x248`，相差 24 字节。仅有身份提示 ACK 不足以弥补这个差异。

对原生库的隔离副本只修改虚拟地址 `0xcf48` 的一条 ARM64 指令，由 `ADD x0,x0,#0x248` 改为 `ADD x0,x0,#0x230`。沿用原 QQ HOME，没有清空、重建或更换登录数据。连续三次独立启动分别约 9、8、8 秒获得真实 `loggedIn=true`，OneBot `get_login_info` 的账号匹配，`get_status.online=true`。未发送 QQ 消息或调用模型。这验证了账号识别适配的重复性，尚不能代替实际收发验收。

维护源码将这个适配放在启动前自动生成独立副本，原始上游 `.so` 不覆盖。仅对 QQ `3.2.34-53644`、固定 wrapper 哈希及固定 SnowLuma 源文件哈希启用；校验 ELF 及预期指令，写入后再校验完整结果哈希。并发账号使用独立暂存文件和原子替换；已生成副本每次启动校验，损坏时从原件重建。其他 QQ 版本不应用该偏移，文件不符不尝试猜测适配，也不制造在线状态。
