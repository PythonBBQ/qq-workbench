## 当日曾观察到：隔离旧 QQ 登录环境后恢复

以下失败对照为修复前记录。本轮随后在同版应用、同一套 QQ 3.2.34 与 SnowLuma 1.14.22 运行库上，将原 QQ HOME 完整改名保留，创建空的 QQ HOME，并让用户重新完成官方登录。没有清空工作台设置、API 卡片、记忆或 1.0.7 音色，也没有卸载应用或修改其他 Android 用户。

原环境保留于容器 `/root/.local/share/qqwb-snow-before-fresh-login-20261105`，当前环境为 `/root/.local/share/qqwb-snow`。设备上的 `fresh-login-profile-check.json` 记录了隔离范围。收尾只读核验确认原环境备份和新环境都存在。

重新登录后，SnowLuma 对真实账号返回 `connected=true, loggedIn=true, status=online`；工作台返回 `connected=true`，身份与在线状态核验通过，自动回复保持开启，处理空闲且无最后错误。用户在收到连续私聊测试请求后明确回复“可以了”。这证明本次手机实际聊天已恢复，不再只有 QQ 图形界面登录成功。

当时同一设备和运行库下，旧环境无法识别会话，新环境可以；这只是一次恢复对照，尚未细分到具体缓存文件或数据项，也未完成重启后的恢复验证。次日复发说明不能把旧环境直接认定为根因。此前单纯换库、改加载顺序的对照均未修复。

本次为设备侧可恢复修复，没有发布新 APK、推送 GitHub，也没有将失败的诊断加载器打包。没有另发测试 QQ 消息或主动调用付费模型；用户自己的聊天产生正常模型调用。锁屏、网络切换和长期后台稳定性未在本轮完成验收，不据此扩大结论。

## 已观察到

- 本地工作台接口可达，QQ 窗口可以显示新到消息，但 SnowLuma 仍为管道连接、账号未就绪。因此消息尚未进入模型请求阶段。
- 在应用自己的 QQ 进程中，只读检查原生模块状态：运行时目标已经解析，账号会话尚未识别，没有观察到接收回调。不能根据模块已加载或身份提示 ACK 宣称在线。
- 原生模块启动时保存的服务候选数为 2；登录后使用官方只读解析器重新解析同一进程，服务候选数为 8。这支持继续检查启动过早、候选对象缓存的问题，但尚不构成修复成功证明。
- 对该进程发送身份提示仅得到 ACK，未得到账号就绪事件，不能用缓存账号绕过在线核验。

## 对照测试注意事项

临时延迟加载器必须在主进程中清除 `LD_PRELOAD` 的继承，否则 Electron 子进程会提前映射加载器，出现 `partition_address_space.cc` 致命错误。这属于诊断启动方式的问题，不能归为原 QQ 或原生组件已验证的兼容性结论。

通过 Windows ADB 标准输入写入二进制可能截断；本次改用 Base64 文本传输并回读 SHA256 校验。未校验的临时库不得用于结论或打包。

本轮不修改原账号、模型卡片、记忆及 1.0.7 音色，不向 QQ 发送消息，不调用付费模型。失败的诊断加载器不进入发行资源。

## 新增对照结果

- 修正后的主进程专用加载器延迟 60 秒加载官方 1.14.22 模块；QQ 聊天界面正常，模块加载成功，观察 183 秒仍为 `connected=true, loggedIn=false`。因此不能把延迟启动当作修复。
- 同样方式隔离运行官方 2.4.0，观察 182 秒仍未就绪，未替换生产版本。
- 系统 C++ 运行库提前加载的首次测试被中断；重新独立运行并观察 182 秒后，仍为管道连接、账号未就绪。单独提前加载系统 C++ 库没有恢复此设备的消息通道。上游 x64 案例中的 capability 组合未在 Android 上复现，也未改变系统权限。
- 仅针对进程自身的读取后备首次在原生模块加载前触发 Chromium 地址空间错误，该次不构成 native 兼容性结论。随后重新编译诊断计数并校验传输，QQ 界面与原生模块正常启动；观察 182 秒仍未就绪。拦截计数为 0，未观察到该后备实际参与读取，因此不能声称后备生效、读取问题已修复或已全面排除。
- 系统 C++ 库对照中只读状态仍显示运行时目标已解析，但未识别账号会话、未观察到接收回调。候选数量变化不足以证明可收发。

临时测试启动器的重叠会话拒绝分支原先还会在 finally 中按 HOME 清理进程，可能干扰先前的对照。已在本地诊断副本中增加实际启动标记，拒绝重叠时保留已有会话。此问题属于测试启动器，不能作为正式应用聊天不回复的根因。
